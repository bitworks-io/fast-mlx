The improvement loop

Research becomes a feature only after the evidence agrees.

fast-mlx uses agents and automation to accelerate research, implementation, testing, and documentation. Authority remains narrow: an agent may propose or execute an approved slice, but it cannot promote partial evidence or silently expand the product boundary.

One cycle

  1. Intake: capture the technique, pinned sources, and expected user value.
  2. Contract: define the baseline, acceptance criteria, failure paths, and proof commands.
  3. RED: preserve the narrow expected failure before implementation.
  4. GREEN: implement the smallest path that satisfies the contract.
  5. Regression: run predecessor, package, serving, and security checks appropriate to the blast radius.
  6. Loaded proof: when authorized, use clean source/model/workload roots and comparable telemetry.
  7. Decision: promote, shelve, or reject with an explicit dated verdict.
  8. Publication: export only reviewed source and public-safe explanations, then verify the live site.

Failure is a first-class output

A baseline out-of-memory result, a diagnostic benchmark, or a compiler RED can be valuable evidence. It is never permission to substitute a different workload, overwrite the boundary, or claim the feature works. The next cycle starts from the preserved result.

What “self-improving” means

The project can repeatedly research, plan, implement, test, review, and publish through a durable workflow. It does not grant itself credentials, bypass review, modify a production environment, or treat its own generated text as proof. Improvement is continuous; authority and evidence remain explicit.
