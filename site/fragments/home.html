The system

A closed learning loop, not a benchmark highlight reel.

  1. 01

    Research

    Pin the paper, implementation, workload, and user hypothesis.

  2. 02

    Design

    Define correctness, quality, resource, security, and rollback boundaries.

  3. 03

    Implement

    Start with a failing contract and add the smallest candidate path.

  4. 04

    Verify

    Run focused and regression tests before any loaded measurement.

  5. 05

    Measure

    Compare identical source, model, prompts, cache state, and hardware.

  6. 06

    Decide

    Promote, shelve, or reject. Partial evidence never crosses the gate.

  7. 07

    Publish

    Ship source, tests, a dated note, and a public-safe evidence boundary.

Current foundation

The public site shows performance, feature set, and value at a glance.

The codebase combines an OpenAI-compatible HTTP/SSE server, continuous batching, exact cache controls, capacity planning, and a harness that measures output parity, distribution drift, task behavior, throughput, memory, and long-running service health so the public site can explain what is fast, what is shipped, and what remains gated.

The useful failures stay visible

A 15× local speedup can still be the wrong product path.

fast-mlx evaluates the whole request and the whole quality boundary. A faster kernel can lose on prefill, capacity, task behavior, thermal equality, or operating cost. Those results are recorded instead of being quietly deleted.
