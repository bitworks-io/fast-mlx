The local-LLM model ladder, benchmarked — on a server verified 27% faster.

We benchmarked ten open-weight models — from 2B to 70B dense, several mixture-of-experts, and a 284B MoE — on a native Apple-Silicon inference server, each at the temperature its own vendor recommends for each task. We isolated what our performance work actually buys per model, ported a frontier speculative decoder and confirmed it correct, and reported every number at its measured size — including the ones that came in below prediction.

Background

The largest opportunity was invisible to the existing benchmarks

The server looked well optimized, but its real workload wasn't being measured.

mlx-serve runs open-weight models on Apple Silicon and speaks the OpenAI and Anthropic APIs — the backend for local agents and a private, on-prem chat tier. Its performance benchmarks were thorough, and they ran entirely at temperature = 0.

Production and agent traffic, however, runs at temperature ≈ 1 — a different, more expensive path through the sampler that no performance benchmark exercised. So the first step was a measurement harness for that path: streaming, temperature‑aware, and concurrency‑aware. It grew into the model-ladder benchmark below, where each model runs at the temperature its vendor recommends for each kind of task. Every figure comes from it, on real hardware, warm, as the median of repeated runs.

The benchmark

The models that back a private LLM tier — measured on their real workloads

The tiers a self-hosted deployment actually chooses between, plus the largest that fits the box.

These are the models from our own model-selection ladder: the dense workhorses (Qwen3-32B — the current production model — and Llama 3.3 70B), the efficient mixture-of-experts picks (Qwen3-30B-A3B, Gemma 4 26B-A4B), a multimodal option (Gemma 3 27B), the smaller tiers, and — as the supported frontier — DeepSeek-V4-Flash, a 284B / 13B-active MoE served through the embedded ds4 engine at 2-bit. Everything runs on one Apple M5 Max, one model resident at a time.

One model from the list is absent for an honest reason: Mistral Small 24B's current MLX checkpoints do not yet load in mlx-serve — its quantized token-embedding trips a Mistral-specific weight-loading gap (Qwen and Gemma quantized embeddings load fine). We report that as a bug to fix, not as a number to estimate.

Temperature, matched to the task

Each model runs at the temperature its own vendor recommends — not one house number. Qwen and Llama publish lower temperatures for coding/math/reasoning and higher for creative writing; Google (Gemma) and Mistral publish a single temperature for all tasks, so their rows don't vary by use case. We follow each model card.

Five use cases

Coding, math, hard reasoning, tool-calling, and creative writing — the shape of real traffic, not a repeat-the-prompt microbenchmark. Tool-calling is measured as the streamed response after a tool result, since the call itself arrives in a single untimed chunk.

Two facts dominate this table. First, decode throughput is essentially flat across use cases for a given model — the recommended temperature and the content type barely move it, because at a fixed generation length the sampler cost is the same. Tool-calling is the one consistent exception (lower, because its response is short and structured). The use-case-and-temperature matching matters for output quality, not decode speed.

Second, and the reason this table exists: architecture, size, and quantization control roughly a 20× throughput range — from Qwen3-4B at 181 tok/s to Llama 3.3 70B at 9. The clearest result for a self-hosted tier is the mixture-of-experts payoff: at the same 4-bit quantization, Qwen3-30B-A3B (3.3B active) runs at ~151 tok/s versus the dense Qwen3-32B's ~28 — about 5.4×. Against the model currently in production (Qwen3-32B at 8-bit, ~15 tok/s) the gap is ~10×, but that figure also trades 8-bit for 4-bit; we measured throughput, not output quality, so we quote the same-quant 5.4× as the architecture win. DeepSeek-V4-Flash — a 284B model at 2-bit — sustains ~36 tok/s on a single Mac through the ds4 engine.

The enhancements, per model

What the optimizations actually buy — measured on each model

The perf work was originally measured on one fast 2B model. Here it is isolated per model, two ways: the optimized server vs a pre-optimization baseline, and speculative decoding on vs off.

optimized vs baselineThe sampler optimizations: +2–3% on fast models, ~0% on large ones

Running each model on the optimized server and on the pre-optimization binary (spec-decode on for both) isolates the L1/L3 sampler-fusion and KV wins. The result is consistent with the design: the optimizations remove a fixed, vocabulary-bound per-token cost, so they are a meaningful slice of a fast decode and negligible on a slow one.

+2.4–3.1%Qwen3-4B, Gemma-4 E4B/26B-A4B, A3B (fast)
+0.4–1.1%Qwen3-8B, Qwen3.6-27B, Gemma 3 27B
~0%Qwen3-32B, Llama 70B (large dense)

This validates the run's headline caveat across the whole ladder: the sampler wins are for the fast tier (small dense, low-active MoE, drafters). On the bandwidth-bound big dense models they are within measurement noise — which is exactly where we said they would be.

workload-specificSpeculative decoding: a large win on agentic edits, neutral on fresh generation

The +27.2% headline is real — but it is measured on the agentic-edit workload, where the model re-emits large spans of an existing file and speculative decoding's n-gram lookup hits constantly. Measured across the whole ladder, that workload runs 1.9–3.1× faster than fresh generation on the same model — the production Qwen3-32B-8bit does 45 tok/s editing vs 15 generating; Qwen3-8B does 191 vs 62. On fresh generation, by contrast, the drafted tokens rarely match, so speculation is within measurement noise, neither faster nor slower (Qwen3-8B 63.0 on vs 63.0 off; A3B 151.8 vs 151.2). The one place it carries a small, consistent cost is the short structured tool-call path, where the lookup runs but rarely pays.

1.9–3.1×agentic-edit / echo, measured across the ladder
≈ neutralcoding / math / reasoning / creative generation
small costshort structured tool-call path

The honest takeaway: speculative decoding is a workload lever, not a free global speedup. It belongs on for agent traffic — file edits, tool-result echoes — where high token overlap lets it reach up to 2–3×; it is a wash on plain generation, and only adds a lookup on the short structured paths (a gate-tuning item). So the per-model table above is the generation floor and the verbatim-echo numbers are the ceiling; real edits land between the two, scaling with how much of the file is unchanged.

correct, boundary foundTrained drafters: the 8B result is not the general one

DSpark, the ported frontier drafter, is correct and byte-equivalent — but its "no batch-1 win" result was specific to Qwen3-8B, where the target decodes in ~16 ms and the drafter's own overhead dominates the round. The slow big models are the opposite, favorable regime: on Qwen3-32B (~65 ms/token) that fixed drafter overhead is a small fraction of the round. We could not measure it directly — no DSpark drafter for Qwen3-32B exists — but published EAGLE-3 drafters for Qwen3-32B do (AngelSlim, RedHat), and they report a ~1.7–1.9× speedup on vLLM/SGLang. So a real speculative win on the production model is externally demonstrated; what blocks it here is that mlx-serve has no EAGLE-3 draft path yet (only n-gram PLD, a Gemma-4 drafter, and Qwen3.5/3.6 native MTP) — a scoped, tracked follow-up, not a dead end.

DeepSeek-V4-Flash runs through a separate engine (ds4, in C), so the MLX sampler optimizations don't apply to it; it carries its own native multi-token-prediction and sustains ~36 tok/s regardless. We keep those boundaries explicit rather than imply one optimization covers every model.

Under real load

Beyond one stream: concurrency, memory, and long sessions

The numbers that decide what fits on the box and how it holds up with more than one user and a growing context.

Concurrency scales aggregate throughput ~2.8× from one stream to eight on the batchable dense models — the server folds concurrent decodes into one forward pass. Per-stream latency trades off as users are added (each stream slows), but total tokens served climbs: eight users of Qwen3-32B-8bit get ~43 tok/s combined, about what a single user gets on the agentic-edit path. Mixture-of-experts models don't batch this way in mlx-serve today, so this lever is for the dense tier.

Memory footprint — what fits on 128 GB

Resident weights: Qwen3-4B 2.1 GB · Gemma-4 E4B 4.8 · Qwen3-8B-8bit 8.1 · the 27–32B tier 14–17 · Qwen3-32B-8bit 32 · Llama 70B 37 · DeepSeek-V4-Flash (2-bit) 81. Every one fits the 115 GB tuned ceiling with room for KV cache — the 70B and the 284B MoE included.

Time-to-first-token stays low

Prefill runs at hundreds to ~190,000 tok/s (it accelerates with prompt length as the batch fills), so the latency before a reply starts is ~45 ms on a short prompt and still only ~70 ms at 13K tokens of context.

Decode holds up as sessions grow

On Qwen3-8B-8bit, decode eases from 63.8 tok/s at a fresh prompt to 52.9 at 13K tokens of filled context — a gentle ~17% decline, not a cliff. Long agentic sessions stay responsive; kv-quant is on the shelf if contexts push much further.

What the numbers showed

Results that didn't match the initial expectation

Three findings that are easy to leave out of a summary — and part of why the five above are trustworthy.

rejected by dataA proposed optimization we did not ship

An independent review proposed suspending speculative decoding when requests arrive together, so they would batch — a standard throughput argument, roughly 1.5× on paper. We measured it first. On the real workload, speculation was effective enough that even serialized it outperformed the batched path:

514tok/s · speculation on, serialized
274–403tok/s · batched, speculation off

Shipping it would have regressed the most common workload in exchange for a benchmark that did not reflect production. Rejecting it cost nothing, because the measurement came before the implementation.

real, below predictionThe kv-quant lever: a roofline predicted 15–40%

The review's model predicted a 15–40% long-context gain from reading the KV cache in quantized form instead of expanding it to dense on every token. We implemented it — including rewriting a grouped-attention step that would otherwise have materialized the copy it was meant to avoid — then measured at 16K and 32K context and reported the result:

+3.1%@ 32K context (vs dense)
~0%@ 15K context
15–40%the roofline's prediction

The gap has a clear cause: at batch‑1 the decode is dominated by the 8 GB weight read, not the KV cache, so the bandwidth saving is a small fraction of total bytes moved. The gain is real and grows with context — it turns kv-quant from a potential long-context loss into a small win — but it is +3%, not +30%, which is the figure we report.

correct, boundary foundThe frontier drafter: correct, faster on its own path, and bounded

We ported DSpark — a modern EAGLE-3-style speculative drafter — including the loader, backbone, and full verify loop, and verified it correct against the published 8B checkpoint: with the drafter on, output is byte-identical to the drafter off across every API surface (a speculative decoder must change only speed, never output). The propose / verify / accept / roll-back / commit machinery is validated, including a test that fails the moment the persistent-cache bookkeeping is wrong.

byte-identicaloutput, drafter on vs off
+24%drafter-path decode (off by default)
no batch-1 winon this 8B target

Its acceptance rate looked low at first — a single "11.4%" figure. Measured correctly, that was an artifact of dividing by the full block width; the drafter actually accepts ~1.5–1.8 tokens per round and predicts the next token about two-thirds of the time. It is not broken. We then investigated the two suspected causes and closed both with data: the rotary-embedding convention was already correct, and a full-precision target did not raise acceptance. The original premise, that acceptance needed tuning, did not hold.

We did find and ship one real speedup: the verify loop was doing a second full model pass on roughly 97% of rounds, which we removed — a +24%, output-identical gain on the drafter's own path. It still does not beat plain decoding on this configuration, and the timing shows why: at batch-1 the target's verify pass dominates each round, and the acceptance rate, while healthy, is not high enough to offset it. We measured the one remaining lever counterfactually before implementing it, found it at break-even, and did not build it. The runtime gate keeps the drafter disabled on this pairing, so there is no regression. The gain depends on a larger, slower target — the favorable regime noted earlier, where published EAGLE-3 drafters already show ~1.7–1.9×; on mlx-serve that path is pending, not claimed here.

measured flatA concurrency fix the hardware made unnecessary

Loading a new prompt can, in principle, stall in-flight streams while it runs — head-of-line blocking. We built the fix, a resumable prefill that interleaves with ongoing decodes and keeps concurrent streams byte-identical, then measured the stall it removes:

46msbefore · 14K-token prefill
46msafter · identical

Prefill on this hardware runs at roughly 265,000 tokens/second, so a 14K prompt loads in under 50ms — below normal decode jitter. The change is correct and kept for the case that needs it (very long contexts or slower hardware), but we are not shipping it as a speedup it does not deliver here. Knowing where a gain is absent is as useful as knowing where it is.

What the process caught

Defects surfaced by the verification discipline

Four defects found through the process. Two had not executed in production, and would have the moment the paths that reach them were enabled.

Silent tensor corruption

A core sampler primitive quietly flattened multi-row inputs — invisible for years because every caller passed one row. Our batched path would have hit it. Caught by a test written to fail on the old behavior, verified red-on-revert.

An all-NaN attention mask

The fused attention path built its causal mask with 0 × -inf = NaN, poisoning every kept position. It had never fired — the path was dead code. Enabling it exposed the bug; the test harness had been silently discarding the NaNs. Fixed and guarded.

A latent compile error

A weight loader called an API that doesn't exist in the toolchain — hidden because the function had never been reached by a test. Validating it against the real checkpoint forced compilation and surfaced it before it could ship.

An invalid test, caught

Our first correctness check for the kv-quant path ran on a model architecture that never reaches that code — so it "passed" trivially. We noticed, re-ran on the architecture that actually engages it, and only then trusted the result.

Undefined behavior, pre-empted

The resumable-prefill change had a one-token edge case that, in an optimized build, is undefined behavior — not a clean crash. Caught in review against the exact class the codebase already documents, and guarded before it reached a build.

The cluster tier

What we could not run on one Mac — reported as specs, not numbers

The ladder above is what fits and runs on a single 128 GB Mac. Two groups from the same selection list do not, and we say so rather than invent figures. GLM-4.5-Air and Phi-4 use architectures mlx-serve does not yet support, so they fail to load regardless of memory. The genuine giants — Qwen3-235B-A22B, DeepSeek-R1, GLM-4.6, and the Kimi K2 class — run from 235B to 670B-plus parameters; at production-floor quantization they need 200–600 GB and belong on a Mac Studio cluster or GPU nodes, not this box.

What transfers is the mechanism, verified from primary model cards rather than aggregator pages: these are DeepSeek-lineage mixture-of-experts models, and the same external-drafter speculative decoding we ported (DSpark) targets that whole cohort. DeepSeek-V4-Flash — benchmarked above at ~36 tok/s — is the member that already fits, through the ds4 engine at 2-bit. The rest are a hardware-and-architecture roadmap, not a promise of numbers this machine can produce.

Next steps

What's next, scoped from the measurements

draft path
An EAGLE-3 drafter for the big dense models — published EAGLE-3 heads for Qwen3-32B report ~1.7–1.9× on other runtimes, and the slow 32B is exactly the regime where a drafter's fixed overhead is dwarfed by the target forward (the opposite of why it lost on the fast 8B). mlx-serve needs an EAGLE-3 draft path to use them; the re-forward elimination from the DSpark work already applies. This is the concrete route to a speculative win on the production model.
bench run
Long-context kv-quant — the +3% grows with context; the lever now exists and is correct, so measuring the crossover at 64–128K is a bench run, not a build. The interleaved-prefill change is on the same shelf for the day contexts get long enough to need it.
gate tuning
Shed speculative decoding on the paths it can't help — the benchmark showed it is a wash on plain generation and carries a small cost on the short structured tool-call path, where the lookup runs but rarely matches. Tightening the prompt-time gate sheds it there while keeping the agentic-edit win.
deployment
Move the production tier to the MoE pick — the live model is dense Qwen3-32B at ~15 tok/s; Qwen3-30B-A3B delivers ~151 tok/s on the same box — ~5.4× the same-quant dense model, ~10× the current 8-bit config. The model-selection analysis rates its quality comparable; this run measured the throughput, which is the largest single lever here — ahead of any server-side optimization.
Appendix

Test environment and system tuning

Hardware

Apple M5 Max — 18 cores (6 performance + 12 efficiency), unified 128 GB. macOS 26.5.2 (build 25F84).

Software

mlx-serve on Zig 0.16, Apple mlx-c 0.31.2. Optimized build = the shipped perf branch; baseline = the immediate pre-perf-run commit. DeepSeek-V4-Flash via the embedded ds4 (C) engine.

Method

Streaming decode tok/s, one model resident at a time, warm, median of four runs after a discarded warm-up, 256-token generations. Each model at its vendor-recommended temperature per use case; spec-decode at the production default. Full CSV saved alongside this page.

System tuning

The GPU memory ceiling was raised from ~96 GB to 115 GB. On a 128 GB Mac, macOS caps the GPU's wired working set at roughly 75% of RAM by default, which leaves the largest models and their KV cache short of room. We raised it with a single kernel parameter and made it persistent:

sudo sysctl -w iogpu.wired_limit_mb=117760  — installed as a boot-time LaunchDaemon so it survives restarts.

This does not change decode speed on its own — throughput is bandwidth-bound, not allocation-bound — but it is what lets Llama 3.3 70B and the 284B DeepSeek-V4-Flash run with headroom instead of paging. It is the one system-level change behind the numbers above, documented so the environment is fully reproducible.

Summary

A set of changes whose numbers are verifiable.

The +27% matters, and so does the rest of the record: a change shipped only when it was verified identical in output and faster on the real workload; a proposal that would not help was rejected on the evidence; a gain that came in at +3% rather than +30% is reported at +3%, with the reason; a lever measured at break-even before implementation was not built; and the defects were caught by tests rather than in production.

The approach is consistent throughout: measure first, verify every change, review the plan adversarially, and distinguish clearly between what is proven, what is rejected, and what is still pending.

Measure first

Build the benchmark that sees the real workload before touching code. The obvious benchmark missed the whole hot path.

Gate every change

Output-equivalence and a measured win, or it doesn't ship. No unverified claims, no hopeful merges.

Review adversarially

A separate reasoning pass tasked with finding flaws in the plan. It identified the highest-value lever, a trap inside another, and a predicted gain that did not materialize.

Report the boundary

Shipped, rejected, below-prediction, and pending are different outcomes. We don't blur them into "done."
